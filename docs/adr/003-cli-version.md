# ADR-003: CLIフレームワークにおける urfave/cli v3 の採用

## ステータス (Status)
**承認済み (Accepted)**

## 文脈と課題 (Context)
ADR-002 において CLI フレームワークとして `urfave/cli` の採用を決定した。  
導入にあたり、長年利用実績のある安定版 **v2**（`github.com/urfave/cli/v2`）と、設計刷新が行われた **v3**（`github.com/urfave/cli/v3`）のいずれを採択するかの選定が必要となった。

本ツールは ADR-001 にて「1サイトあたり10秒以内の取得完了」という厳格なタイムアウト制御（`context.Context` の活用）を定義しており、新規プロジェクトとして将来的な保守性や技術的負債の排除も考慮する必要がある。

---

## 決定事項 (Decision)
CLIフレームワークのバージョンとして **`github.com/urfave/cli/v3`** を採用する。

### 採用理由
1. **標準 `context.Context` ファーストなシグネチャ**:
   v3 では `Action` 関数のシグネチャが `func(ctx context.Context, cmd *cli.Command) error` に刷新された。第1引数として標準の `context.Context` を直接受け取れるため、ADR-001 で定めた 10 秒タイムアウト（`context.WithTimeout`）や OS シグナルによるキャンセル処理を HTTP クライアントへ極めて自然に伝播させることができる。
2. **新規開発に伴う移行コストの排除**:
   新規立ち上げプロジェクトにおいて既存の v2 コード資産に縛られる理由がない。初期実装から v3 を採用することで、将来発生する可能性のあるメジャーバージョン移行作業（v2 から v3 への書き換え）のコストを未然に防止する。
3. **コマンドモデルの統一性**:
   v3 ではルートコマンドもサブコマンドも同一の `*cli.Command` 型として扱われる。これにより、将来的に Auto-Discovery やキャッシュ管理などのサブコマンドを追加・拡張する際にも一貫した設計を維持しやすい。

---

## 結果と影響 (Consequences)

### メリット (Positive)
* **タイムアウト制御の堅牢化**: `context.Context` がフレームワークの中心にあるため、HTTP 通信の中断やリソース破棄の実装漏れを防ぎやすい。
* **長期的な保守性**: 最新の仕様・設計に追随しているため、今後の機能改善や Go 本体のアップデートに対する親和性が高い。
* **API の整理**: `cli.App` と `cli.Command` の二重管理がなくなり、コードのメンタルモデルが単純化される。

### デメリット・トレードオフ (Negative / Risks)
* **Web 上の情報量**:
  v2 と比較して日本語の技術ブログやコミュニティ記事、Q&A サイトでの作例が少ない。
  * **対応策**: 公式リポジトリのドキュメントおよび examples ディレクトリ、テストコードを一次情報として参照・実装する。
