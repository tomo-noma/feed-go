# ADR-002: CLIフレームワークとしての urfave/cli の採用

## ステータス (Status)
**承認済み (Accepted)**

## 文脈と課題 (Context)
ADR-001 において、実装言語として Go を採用することが決定した。
本ツール（`feed-go`）はコマンドラインツールであるため、以下の要件を満たすCLIフレームワークの選定が必要となる。

* `-f`, `--format` のようなPOSIX準拠の短縮フラグ・ロングフラグの両立。
* わかりやすいヘルプメッセージ（`--help`）やバージョン情報（`--version`）の自動生成。
* 引数・フラグのバリデーションと、統一された終了コード（ADR-001準拠）へのマッピング。
* 小・中規模ツールに適したシンプルな設計と、将来的なサブコマンド追加に耐えうる拡張性。

### 検討した候補
1. **Go標準パッケージ (`flag`)**
   * メリット: 外部依存が一切ない。
   * デメリット: ロングフラグと短縮フラグの併用が難しく、ヘルプ表示のカスタマイズやサブコマンド管理に多くのボイラープレートが必要になる。
2. **`spf13/cobra`**
   * メリット: 大規模OSS（KubernetesやGitHub CLIなど）での採用実績が豊富で、エコシステムが強固。
   * デメリット: 初期ボイラープレート（コマンドごとのファイル分割、`init()` 関数やパッケージグローバル変数の多用）が多く、単一コマンド＋オプション主体のツールには過剰設計（オーバーエンジニアリング）になりやすい。
3. **`urfave/cli`**
   * メリット: 単一の構造体定義（`&cli.App{...}`）でフラグやアクションを宣言的に記述でき、可読性が高い。
   * デメリット: Cobraほど巨大なエコシステムはないが、本ツールの要件に必要な機能はすべて網羅している。

---

## 決定事項 (Decision)
CLIフレームワークとして **`urfave/cli`** を採用する。

### 採用理由
1. **宣言的で直感的なコード構造**:
   `cli.App` 構造体に対して `Flags` や `Action` を宣言的に渡すスタイルであるため、グローバル変数の乱用を防ぎ、依存関係の注入（Dependency Injection）やテストが容易になる。
2. **ツールの規模感との一致**:
   `feed-go` は「URLを受け取り、パースして出力する」というシンプルな責務を持つツールであり、`urfave/cli` の簡潔さが開発速度と保守性のバランスにおいて最も優れている。
3. **必要十分な機能群**:
   * 短縮名エイリアス（`Aliases: []string{"f"}`）
   * デフォルト値の設定と環境変数のバインド（`EnvVars`）
   * 構造化されたエラーハンドリング（`cli.Exit("...", code)` による終了コード制御）
4. **依存関係のシンプルさ**:
   `spf13/cobra` + `pflag` + `viper` の組み合わせと比較して、モジュール依存が小さく軽量に保てる。

---

## 結果と影響 (Consequences)

### メリット (Positive)
* **高い可読性と保守性**: `main.go` または `cli` パッケージ内にフラグ定義とエントリーポイントがコンパクトにまとまり、コードの見通しが良くなる。
* **終了コード制御の親和性**: ADR-001 で定義した終了コード（1〜4）を、`cli.Exit` や独自エラー型を通じて統一的にシェルへ返却しやすい。
* **拡張性の確保**: 将来的にサブコマンド（例: `feed-go add <url>` や `feed-go discover <url>`）を追加する場合も、`Commands: []*cli.Command{...}` を追加するだけで破壊的変更なく移行できる。

### デメリット・トレードオフ (Negative / Risks)
* **メジャーバージョンの仕様差**:
  `urfave/cli` には v2 と v3 が存在し、Action関数のシグネチャやContextの受け渡し手法が異なるため、プロジェクト開始時にバージョンを明示的に固定する必要がある。
