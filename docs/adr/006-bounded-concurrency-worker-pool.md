# ADR-006: セマフォ制御を用いた制限付き並行フィード取得（Worker Pool）の採用

## ステータス (Status)
**承認済み (Accepted)**

## 文脈と課題 (Context)
システム設計書では、複数URL指定時も1URLずつ順次処理を行う直列ストリーム処理として設計されていた[cite: 4]。  
しかし、運用上以下のトレードオフが存在した：
1. **レイテンシの増大**: 1サイトあたり最大10秒のタイムアウト制約が設けられているため[cite: 1, 3, 4, 5]、多数のURL（例: 10〜20件）を直列に処理すると、通信遅延やタイムアウトが重なった場合に全体の所要時間が数分単位に跳ね上がるリスクがある。
2. **リソース制約の厳守**: 常駐メモリ30MB以下という非機能要件を満たす必要があり[cite: 1, 3, 4]、無制限に Goroutine を立ち上げる並行処理はメモリ使用量の急増を招く恐れがある。

## 決定事項 (Decision)
**バッファ付きチャネル（セマフォ）を用いた「同時実行数制限付き並行処理（Worker Pool）」**を採用する。

1. **最大同時実行数の制限**:
   * 同時並行数を **4**（デフォルト）に制限する。
   * フィード1件の処理に必要なメモリは数MB程度であるため、4並行であればピーク時でも非機能要件の「30MB以下」を確実に達成可能とする[cite: 1, 3, 4]。
2. **並行処理と集約の構造**:
   * 各URLの「HTTP通信（`internal/fetcher`） $\rightarrow$ パース・サニタイズ（`internal/parser`）」を個別の Goroutine で並行実行する[cite: 4]。
   * 取得結果スライスへの追加およびエラーリストの収集は、排他制御（`sync.Mutex`）を用いてスレッドセーフに集約する。
   * 入力URLの順序性を担保するため、各取得結果に元のURLインデックスを保持して結合する。
3. **コンテキスト伝播と中断制御**:
   * `urfave/cli/v3` から渡されるルートの `context.Context` を全 Goroutine に伝播させ、OSシグナル（SIGINT/Ctrl+C）受信時には全ワーカーを即座に安全破棄する[cite: 1, 4, 7]。

## 結果と影響 (Consequences)
### メリット (Positive)
* **スループットの大幅な向上**: 複数URL指定時の総処理時間が直列処理と比較して大幅に短縮される。
* **メモリ安全性の担保**: 同時実行数が物理的に制限されるため、指定URL数が増加してもメモリフットプリントが線形増加せず、30MB制限を遵守できる[cite: 1, 3, 4]。

### デメリット・トレードオフ (Negative / Risks)
* **実装の複雑化**: Goroutine の並行制御、競合状態（Race Condition）、およびリソースリークを防ぐためのテスト（`go test -race`、`uber-go/goleak`）の徹底が必須となる[cite: 1, 4]。
