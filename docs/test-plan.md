# コマンドラインフィード取得ツール（feed-go）テスト計画書

## 1. 文書概要
### 1.1 目的
本書は、コマンドラインフィード取得ツール（`feed-go`）の品質保証を目的としたテスト計画書である[cite: 6]。要件定義書、システム設計書、および各種ADR（ADR-001〜007）に記載された機能要件、非機能要件、終了コード体系、ストリーム制御、制限付き並行処理、部分成功ハンドリング、マルチプラットフォーム自動配布を検証するためのテスト戦略、テスト項目、環境、データ設計、合否判定基準を定義する[cite: 1, 6]。

### 1.2 背景と品質目標
本ツールはシェルスクリプトやCI/CDパイプライン、定期バッチ処理などの自動化ワークフローへの組み込みを主用途としている[cite: 6]。そのため、通常のWebアプリケーションとは異なり、以下の特性を最重要品質基準として検証する。
* **ストリーム分離の厳格性:** 正常系出力（標準出力）にログや警告が一切混入しないこと[cite: 6]。
* **部分成功と終了コード優先度:** ADR-005に基づき、複数URL実行時に一部失敗しても正常データを出力し、優先度（Code 1 > 2 > 3 > 4）に従って正確な終了コードを返却すること[cite: 1, 9]。
* **並行性とリソース制御:** ADR-006に基づき、Goroutineセマフォにより最大4並行を厳守し、入力URL順序を保持した出力とメモリ30MB以下の制限を満たすこと[cite: 1, 11]。
* **データ競合・リーク皆無:** `go test -race` および `goleak` によりデータ競合やソケット/Goroutineの滞留が皆無であること[cite: 1, 6]。
* **リリースアーティファクトの完全性:** ADR-007に基づき、GoReleaserで自動生成された全OSアーカイブとSHA-256チェックサムが整合すること[cite: 1, 7]。

## 2. テストスコープ
### 2.1 テスト対象（In-Scope）
* **CLIインターフェースレイヤー (`internal/cli`):**
  * `urfave/cli/v3` による宣言的フラグ構文解析（`-f`, `-o`, `-t`, `-l`）[cite: 2, 6]
  * URL引数の必須チェックおよび未知オプションの検知[cite: 3, 6]
  * ルートコマンド実行時の `context.Context` 伝播[cite: 2, 6]
* **並行制御および集約処理 (`internal/cli/runner.go`):**
  * セマフォによる同時実行数（最大4）制限の遵守[cite: 1, 11]
  * 複数並行処理完了後の、元URLインデックスに基づく出力順序の整合性[cite: 1, 11]
  * `context.Context` キャンセル（SIGINT等）時の全ワーカー即時中断[cite: 1, 11]
* **部分成功（エラースキップ）制御 (`internal/cli`, `internal/exitcode`):**
  * 一部URL障害時における正常フィード記事のみのstdout出力[cite: 1, 9]
  * 発生した複数エラーに対する終了コード優先度順位の解決[cite: 1, 9]
* **ネットワーク制御レイヤー (`internal/fetcher`):**
  * HTTP/HTTPS通信、User-Agentヘッダー検証[cite: 5, 6]
  * HTTP 3xx リダイレクト制御（最大5回追跡、6回目中断、循環リダイレクト検知）[cite: 5, 6]
  * 段階的タイムアウト制御（Connect 3秒 / Read 7秒 / 全体10秒）[cite: 5, 6]
  * タイムアウトおよびエラー発生時の `io.ReadCloser` 即時クローズ[cite: 3, 6]
* **フィード解析・サニタイズレイヤー (`internal/parser`):**
  * `mmcdole/gofeed` (v1.3.0) を用いた各種フィードのパース[cite: 6, 10]
  * 取得元フィールド優先度検証（Description 優先、フォールバック Content）[cite: 6, 10]
  * 日時正規化検証（UTC基準 ISO 8601 / RFC 3339 形式への変換）[cite: 6, 10]
  * HTMLサニタイズ（`<script>` / `<style>` の本文ごと破棄、ブロック要素境界への改行挿入、連続空白の単一化、空行圧縮）[cite: 6, 10]
* **出力フォーマッターレイヤー (`internal/formatter`):**
  * JSON配列出力（2スペースインデント、UTF-8）[cite: 3, 6]
  * CSV出力（RFC 4180完全準拠、CRLF改行、ヘッダー行、カンマ・引用符・改行のエスケープ処理）[cite: 3, 6]
* **リリース自動化パイプライン (GoReleaser / GitHub Actions):**
  * 各OS向けアーカイブ（`.tar.gz` / `.zip`）の展開および実行可能性[cite: 1, 7]
  * `checksums.txt`（SHA-256）と各配布ファイルのハッシュ値一致検証[cite: 1, 7]
* **非機能要件:**
  * 起動オーバーヘッド50ms以下、メモリ30MB以下の遵守[cite: 5, 6]
  * `go test -race` による競合検証[cite: 1, 6]

### 2.2 テスト対象外（Out-of-Scope）
* フィード自動検出（Auto-Discovery）機能（次期フェーズ優先実装）[cite: 5, 6]
* UTF-8以外の文字コード（Shift_JIS, EUC-JP等）からの自動変換（次期フェーズ優先実装）[cite: 5, 6]
* 外部の実フィード配信サーバーに対する恒常的な依存（テスト環境はローカルモックサーバーで完結）[cite: 6]

## 3. テスト戦略およびテストレベル
```text
[レベル1: 単体テスト (Unit Test)]
   ├── internal/fetcher: HTTPクライアント、タイムアウト、リダイレクト追跡
   ├── internal/parser: HTMLトークナイズ、タグ除去、空白改行正規化、スキーママッピング
   ├── internal/formatter: JSON/CSV (RFC 4180) シリアライズ
   └── internal/exitcode: priority.go による終了コード優先度判定ロジック

[レベル2: 結合テスト (Integration Test)]
   ├── internal/cli/runner.go: セマフォ4並行、URL順序ソート、部分成功データ集約
   ├── ローカルHTTPモックサーバー (net/http/httptest) との結合ストリームパイプライン検証
   └── go test -race によるデータ競合検出、goleak によるGoroutineリーク検証

[レベル3: システム/E2Eテスト (CLI E2E Test)]
   ├── コンパイル済み静的バイナリ (CGO_ENABLED=0) を実行
   ├── 複数URL指定時の stdout (部分成功データ) / stderr (エラーログ) / 終了コードの検証
   └── シェル連携検証 (feed-go ... | jq ., 出力リダイレクト, パイプ処理)

[レベル4: 非機能・リリーステスト (Non-Functional & Release Test)]
   ├── パフォーマンステスト (Hyperfine による起動時間計測)
   ├── メモリプロファイリング (10件並行処理時のRSS 30MB制約検証)
   └── リリース自動化検証 (GoReleaser snapshot ビルド、チェックサム検証)
```

### 5.4 出力フォーマッターテスト (internal/formatter)
* **JSON:** ルートが配列形式、2スペースインデント、UTC日時正規表現合致、マルチバイト文字がエスケープされないこと。
* **CSV:** 1行目が `title,url,published_at,summary,author,feed_title` であること、改行コードが厳密にCRLF（`\r\n`）であること、カンマ・ダブルクォート・改行がRFC 4180に沿って適切にエスケープされること。

### 5.7 非機能要件テスト
* **並行実行時のメモリ制約検証:**
  * 10件の巨大フィード（約5MB/件）を同時指定して並行実行した際、4並行セマフォ制御により最大常駐メモリサイズ（RSS）が **30MB以下** に保たれることを確認（Linux: `/usr/bin/time -v`）。
* **データ競合およびGoroutineリーク検証:**
  * `go test -race ./...` を実行し、並行集約処理（sync.Mutex周辺）においてデータ競合が一切検出されないこと。
  * 複数URL処理の完了後に `goleak.VerifyNone(t)` を実行し、残留するGoroutineが存在しないことを確認。
* **起動時間オーバーヘッド検証:**
  * `hyperfine 'feed-go --version'` の中央値が **30ms以下**、ローカル通信時の中央値が **50ms以下** であること。
* **リリースアーティファクト整合性検証:**

## 9. テスト実施体制およびリスク対策
| 想定リスク | 影響度 | 対策方針 |
| :--- | :--- | :--- |
| **並行処理に伴う競合・デッドロック** | 高 | `sync.Mutex` のスコープを極小化し、CIパイプラインにおいて `go test -race` を必須化する。 |
| **部分成功時のストリーム汚染** | 高 | 取得失敗したURLのレスポンスは集約スライスに含めず、標準エラー出力へのみ出力することをE2Eテストで厳格に検証する。 |
| **外部通信によるFlaky Test** | 高 | 外部Webサーバーへの実リクエストを行わず、ローカルの `httptest.Server` のみを使用する。 |
| **マルチOS配布物の実行権限欠落** | 中 | GoReleaser のアーカイブ生成オプションにより、Unix系バイナリの実行権限（`0755`）が保持されていることをCI上で自動検証する。 |
